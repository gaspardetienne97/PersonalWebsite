## MPC diagnostic recipe (owner, five minutes)

1. Connect the MPC One+ over USB, open `/music/connect`, Enable MIDI. Both MPC ports appear; set the note port's instrument to MPC and tick Ignore on the other.
2. Under Pad notes, press **Learn pads**, then hit A01 to A16 in order (bottom-left to top-right). The grid fills with the note each pad sends. If any two pads share a note the learn stops; that is a program problem on the MPC, not the app.
3. Alternatively pick a preset: if the live monitor shows 37 for A01 and 38 for A06, choose Akai Classic MPC map.
4. Open `/music/play/mpc`, Single strokes: pads 36 and 38 should now be A01 and A03 physically. The grid lights the pad you hit while it is down.
5. Groove copy-back: play the one-bar kick/snare/hat reference back; the result must show matched hits, not all missed. If it still misses, note whether the "extra" count is non-zero (two ports both delivering) and send the live monitor lines.

## Follow-up, 18 September: "the learned map never stuck, and pads stopped responding on other routes"

Reproduced with a fake Web MIDI device (two ports named "MPC One+ Public/Private", Akai Classic notes on channel 10) driven through the real app in Chromium, the same sequence the owner ran.

- **The map did stick.** After Learn pads the profile row in IndexedDB held `padNotes: [37, 36, 42, 82, …]`, survived a reload, and Connect showed "Akai Classic MPC map". One display defect was real: a learned map that matches no preset rendered its "Learned from this device" option after the select's value was set, so the select could fall back to the first entry. The option is now always present (disabled until a map is learned).
- **Client-side navigation worked.** Connect → Practice → Drills → MPC Rudiments, note 37 lit pad 36 and completed step 1; note 38 lit pad 41. The rewrite, the router and the grid are correct.
- **A fresh page load lost MIDI.** MIDI was only ever enabled by a button press (Connect, or the "Enable MIDI" button inside each drill's setup, which is collapsed once a drill is ready). After any full load of a drill route, the runtime started with MIDI off and nothing re-requested it, even though the browser had already granted permission. That is the "channel dropped" experience: on the dev server the known Guide → Practice HMR crash forces exactly such a reload, and so does opening a bookmarked drill.
- **Fix in tree.** The runtime remembers the first successful enable in local state (`music.midi.wanted`) and, on startup after settings load, re-enables MIDI when that flag is set and the browser's permission is not "denied" (`midiPermissionState()` reads the Permissions API, "unknown" where it has no `midi` entry). No prompt is forced on a browser that has never granted. Tests: `_runtime.svelte.test.ts` "MIDI comes back on a fresh load" (re-enables on granted; stays quiet when never enabled or denied). Simulation after the fix: fresh load of `/music/play/mpc`, no click, note 37 → pad 36 lit and step completed, input pill reads MIDI.
- **Still open for the real device.** Two MPC ports: if the note port is the one marked Ignore, nothing arrives anywhere; the Connect live monitor shows which port carries notes. Recipe step 1 stands.

## Follow-up, 18 September (third round): the MPC only talks while the app talks to it

Owner report: the Connect live monitor shows nothing from the Private port until the Private *output* is chosen in the MPC hardware panel and "Connect (init + heartbeat)" is pressed; on drills the input pill stays On-screen.

- **Root cause (source, matches the report exactly).** In Controller Mode the MPC One+ sends pad notes only while a host keeps the captured handshake alive: the init frames once, then a heartbeat frame about every second (this is what the MPC 3 desktop app does). That handshake lived in `MpcHardwareDiagnostic.svelte`: a `setInterval` started by the Connect button and cleared in `onDestroy`. Leaving the Connect page stopped the heartbeat, the MPC dropped out of the link, and every drill saw silence. This was the "input dropped on navigation" from the first report.
- **Fix in tree.** The link is a saved device setting (`DeviceProfile.controllerLink` on the output port) that the runtime honours app-wide: on startup and on every MIDI state change it replays the init handshake and runs the heartbeat on the linked output while MIDI is on with SysEx, and stops it on dispose. The Connect panel's button became **Keep linked (init + heartbeat)** / **Unlink**; the drills' MIDI line shows "MPC linked on MPC One+ Private". Tests: runtime "MPC controller link" (init frames, heartbeat cadence, stop on dispose, nothing without SysEx or a link), the diagnostic's Keep linked / Unlink, device-profile persistence of the flag; 91 tests pass across the touched suites.
- **What the owner should see.** Connect → MPC hardware → choose "MPC One+ Private" (output) → Keep linked. From then on every page keeps the MPC alive; the Private input's notes appear in the live monitor and in the drills' trace line without visiting Connect again.
- **Caveat.** The handshake is a literal capture from MPC 3, replayed in full; which frames the hardware strictly needs is unknown. If the MPC still drops out after a while, the heartbeat interval (1 s) is the value to compare against a trace of MPC 3.

**Owner confirmation, 18 September 02:05.** With the Private output kept linked from Connect, the MPC One+ drives Rudiments on the real hardware. O19, O20 and O21 are closed at the instrument; the remaining MPC items (velocity bands, groove copy-back scoring on the real pads) can now be checked in the ordinary way.
